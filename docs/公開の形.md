# 公開の形

`data/seido.csv` を、GitHub Pages に置く一式に直す。作るのは `futoko_lod/publish.py`、公開するのは GitHub Actions の `pages`。ここで項目を足したり直したりはしない。元は `build.py` が作る JSON-LD の節だけ。

## URI の決まり

土台は `https://h-kazuki-pixel.github.io/futoko-shien-lod/`(`build.py` の `BASE` と同じ)。

| 何の URI か | 書式 | 引くと返るもの |
|---|---|---|
| 1件(1市町村の1制度) | `{土台}id/{id}` | 1件のページ(`id/{id}/index.html`)。JSON-LD を埋め込んである |
| 1件のデータ | `{土台}id/{id}.ttl`、`{土台}id/{id}.jsonld` | その1件と、つないだ市町村の節 |
| 語彙 | `{土台}ns#{名前}` | 説明のページ(`ns.html`)。同じ中身の Turtle は `ns.ttl` |
| データセット | `{土台}#dataset` | 入口のページ。説明(DCAT)は `dataset.ttl` |
| 全件 | `{土台}seido.csv`、`seido.jsonld`、`seido.ttl` | |

`{id}` は `市町村コード-種類`(`docs/データの項目.md`)。id は変えない。制度が無くなっても行を消さず、状態を変える。

## 1件の型

1件は「確かめた記録」(`fsl:Record`)。全件(11/16 夕の時点で133件)がこの型を持つ。そのうち、制度があると確かめた行(状態が あり・予定)だけが、schema.org の `GovernmentService` でもある。「なし」「確認できず」の行を、制度として数えさせないため。

制度の数を数えるときの例(rdflib):

```python
import rdflib
g = rdflib.Graph().parse("https://h-kazuki-pixel.github.io/futoko-shien-lod/seido.ttl")
q = """
PREFIX fsl: <https://h-kazuki-pixel.github.io/futoko-shien-lod/ns#>
PREFIX schema: <https://schema.org/>
SELECT ?area ?kind ?status WHERE {
  ?r a fsl:Record ; schema:areaServed ?area ; fsl:kind ?kind ; fsl:status ?status .
  FILTER(?status = fsl:status-kakunin-dekizu)   # 確認できず。「無い」ではない
}"""
for row in g.query(q):
    print(*row)
```

文字列には言語(ja)が付く。id と補助率には付かない。「探した場所」は IRI。

## つなぐ先

| つなぐ先 | 述語 | 確かめ方 |
|---|---|---|
| e-Stat 統計LOD の標準地域コード | `schema:areaServed` | 台帳の61のコードを実際に引き、名前が合うことを確かめた(`links`) |
| DBpedia Japanese の市町村の資源 | `schema:sameAs`(市町村の節に付ける) | 名前から URI を作らない。資源が持つ地方公共団体コード(`prop-ja:コード`)がこちらのコードと合い、名前も合うものだけを採る。61件すべてが一致(`dbpedia`、`data/dbpedia.csv`)。川崎町と広川町は、かっこ付きの名前の資源だった |

e-Stat の URI は地域コードを、DBpedia の資源は自治体そのものを表す。厳密に同じものとは言い切れないので、`owl:sameAs` は使わず、schema.org の `sameAs` で持つ。

## 隣り合う市町村(11/17。弱い所 点7・8)

DBpedia Japanese の市町村の資源が持つ「隣接自治体」(`http://ja.dbpedia.org/property/隣接自治体`)を引き、名前を台帳のコードに直して `data/rinsetsu.csv` に置く(`python -m futoko_lod.dbpedia --neighbors write`、Actions の `dbpedia`)。

- 使うのは、両方の市町村が互いを隣と書いている組だけ(福岡県内で143組)。片方だけの組、県外、台帳と合わない名前(合併前の町の名前など)は、判定を付けて記録に残し、使わない
- 県名は47都道府県の形だけを見る(「太宰府市」の「府」を県と取り違えた誤りを直した)
- 1件ごとのページに「隣の市町村の同じ種類」、組み合わせの例に「隣り合う市町と並べる」を出す
- **DBpedia Japanese は CC BY-SA 3.0**(元は2022年12月の Wikipedia 日本語版)。このデータ本体(CC BY 4.0)と RDF には入れない。`rinsetsu.csv` だけを CC BY-SA 3.0 として公開し、ページに出どころを書く
- 隣で「あり」でも、こちらにあるとは言えない。探す順番の目安にとどめる

## 確かめた記録を RDF に(11/16 夜。弱い所 公5)

公開するファイル(全件の `seido.jsonld`・`seido.ttl`、1件ごとの `.jsonld`・`.ttl`)では、1件の記録から `fsl:checkActivity` で、確かめた活動(`prov:Activity`)につなぐ。活動は3種類で、どれも記録の URI に `#` を付けた URI を持つ。

| 活動 | URI | 持つもの |
|---|---|---|
| 取り直し(`fsl:Refetch`) | `#refetch-1` など | 役割(出典 / 出典2 / 探した場所)、取りに行った URL(`prov:used`)、取得した日時(`prov:endedAtTime`)、取得できたか、照合の結果 |
| 人の再確認(`fsl:HumanReview`) | `#review` | 見比べる項目の数、見比べた数、合っている・違う・分からないの数、日付 |
| 問い合わせ(`fsl:Inquiry`) | `#inquiry-1` など | 日付、担当課(課の名前だけ)、方法、回答があったか。**回答の文面は出さない** |

取り直しは毎週記録が変わるので、リポジトリの `data/seido.jsonld` には入れない(公開するときに足す)。

## ほかの語彙との対応(11/16 夜。弱い所 点5)

項目ごとに、デジタル庁の政府相互運用性フレームワーク(GIF)の「行政サービス・制度」(実装データモデル、2026-10-06 改定)、欧州の CPSV-AP 3.2.0、schema.org、Dublin Core、SKOS と見比べた。表は `data/goi_taiou.csv`、種類ごとの GIF サービスカタログの分類は `data/goi_taiou_shurui.csv`。語彙のページ(`ns`)の末尾にも出し、2つの CSV も公開する。

- 合い方は4つ: 同じ / 同じ(下位の性質) / 近い / 対応なし。「近い」は、意味は重なるが、持ち方(文字列か節か、単位)か範囲が違うもの
- RDF の上で結んだのは3つだけ: `fsl:kind` → `schema:category`、`fsl:note` → `skos:note`、`fsl:dateChecked` → `dct:date`(`rdfs:subPropertyOf`)。意味がはっきり合うものに限った
- GIF は項目ごとの IRI を持たない(配布は docx・xlsx・xsd)ので、名前で示す。GIF の解説書には、欧州の CPSV を元にしたとある
- CPSV-AP の公開サービスの型(`cpsv:PublicService`)は付けない。CPSV-AP では説明と所管の組織が必須で、このデータは持たない
- 状態(のうち、なし・確認できず)、補助の形、開始、根拠の箇所、第2の出典、探した場所、なしの根拠、確認方法は、どの語彙にも当たるものが無い。確かめた記録を残す、このデータの独自の部分
- 種類と GIF サービスカタログの分類の当て方は、このデータの作者が決めた。GIF が決めたものではない
- 見比べるときに読んだもの: GIF の GitHub(digital-go-jp/GIF、コミット b979fcd、CC0)の 451-4 と 491-1、CPSV-AP 3.2.0 の SHACL(semiceu/CPSV-AP)、schema.org の GovernmentService のページ

## ページ

| ページ | 中身 |
|---|---|
| `index.html` | 福岡都市圏の17市町×5種類の表(マスから1件のページへ)、状態の意味、種類ごとの件数、ファイルへのリンク |
| `ichiran/` | 全件の一覧 |
| `id/{id}/` | 1件の項目、出典、根拠の箇所、探した場所、確認日、確認方法。同じ市町のほかの種類へのリンク |
| `ns` | 語彙の説明 |

「確認できず」のページには、「制度が無いという意味ではない」と必ず出す。公式の一覧に載っていないことを根拠にした「なし」には、表では ※ を付け、1件のページでは「市町村が無いと答えたものではない」と必ず出す(どちらもテストで確かめている)。状態は色だけで分けず、文字で書く。

1件のページには、確かめた記録も出す。

| 欄 | 元 | 出すもの |
|---|---|---|
| 人の再確認 | `data/saikakunin.csv` | 人が出典と見比べた項目の数と、判定の内訳 |
| 問い合わせ | `data/toiawase.csv` | 日付、担当課、方法と、回答があったかどうか。**回答の文面は載せない** |
| 定期的な取り直し | `data/torinaoshi/saishin.csv` | 最後に取り直した日(日本時間)と、照合の結果 |

`data/toiawase.csv` の「担当課」は、そのままページに出る。課の名前だけを書き、人の名前を書かない。突き合わせは、「反映したid」があればその id だけ、無ければ同じ市町村・同じ種類の行すべて。

## 確かめていること(`tests/test_publish.py`)

- `GovernmentService` の型を持つのは、あり・予定の行だけ
- 問い合わせの回答の文面が、どの「公開の可否」でもページに出ない

- Turtle と JSON-LD が、同じトリプルになる(全件、1件ごとの組すべて)。1件ごとのファイルを足すと全件になる
- データに出てくる `fsl:` の名前は、すべて語彙(`ns.ttl`)で説明されている。検査(`schema.py`)が許す値も、すべて語彙にある
- 表のマスが、データの状態と合っている。ページの中のリンクが切れていない
- 公開する CSV は `data/seido.csv` そのもの

## 公開の手順

1. はじめに1回だけ、リポジトリの Settings → Pages で Source を「GitHub Actions」にする
2. `data/seido.csv` などが main に入ると、`pages` が検査 → テスト → 書き出し → 公開 → 公開された URL の確認、の順に回る
3. 確認の結果(HTTP、転送の回数、形式、他のサイトからの読み込み)は、実行結果のまとめに出る

手元で見るとき: `python -m futoko_lod.publish`(`_site/` に書き出す。`_site/` はコミットしない)。

## 版(節目のタグ)(11/16)

GitHub Pages に出るのは、いつもいちばん新しい中身だけ。URL は同じまま、中身が変わる。もの(制度)の URI は版が変わっても変えない。

ある時点の中身を指したいときのために、節目で Git のタグを付ける。タグを付けた時点のファイルは、次の固定の URL で取れる。

- `https://raw.githubusercontent.com/h-kazuki-pixel/futoko-shien-lod/{タグ}/data/seido.csv`(JSON-LD は `data/seido.jsonld`)
- 一式: `https://github.com/h-kazuki-pixel/futoko-shien-lod/tree/{タグ}`

タグの名前と付ける時:

| タグ | 付ける時 |
|---|---|
| `v{年}-{月}-{日}`(例 `v2026-11-16`) | 公開データ(`data/seido.csv`)の件数か状態が変わった日。問い合わせの回答を反映した日など。1日に1つまで |
| `v2026-11-17` | Zenodo の最初の版(DOI を付けるため。件数・状態は変わっていない日だが、例外として付けた) |
| `lodc2026` | LODチャレンジの応募フォームを送る直前。審査はこの中身で行われる |

タグは橋本が GitHub の画面で付ける(Releases → Draft a new release → 「Choose a tag」に名前を入れて新しいタグを作る。対象は main)。作業環境からはタグを付けられない。付けたタグは消さない。付け直さない。定期的な取り直しの記録(`data/torinaoshi/sabun.csv`)は、タグの間に何が変わったかの手がかりになる。

## Zenodo で版に DOI を付ける(11/17 に準備。有効にするのは橋本)

Zenodo の GitHub 連携を有効にすると、それより後に作った GitHub のリリースごとに、リポジトリの一式が Zenodo に保管され、DOI が付く。DOI は消えない識別子なので、ある時点の中身を指すのに使える(持続可能性・開放性)。

- 記録の情報は `.zenodo.json` から取られる(Zenodo のヘルプ。`CITATION.cff` もあるが、両方あるときは `.zenodo.json` だけが使われる)。`CITATION.cff` は GitHub の「Cite this repository」のために置いている
- 種類は dataset、ライセンスは CC BY 4.0 にした。保管される一式にはプログラム(MIT)と `rinsetsu.csv`(CC BY-SA 3.0)も入るので、説明の文に書いた
- 作者名は本名 `Hashimoto, Kazuki`、所属は StudySite(橋本、11/17)。橋本の実績として引用されるように。LICENSE と CC BY の表示名(`h-kazuki-pixel`)とは別のままにしている
- 取り込まれるのは、有効にした後の新しいリリース(Zenodo のヘルプの書き方)。既にある `v2026-11-16` は取り込まれない見込み

橋本の手順:

1. https://zenodo.org で、GitHub のアカウントをつないだ状態にする(Zenodo のヘルプでは、つないであることが前提。ログインの画面で GitHub を選べば一度で済むはずだが、こちらでは確かめていない)
2. 右上のプロフィールのメニューから「GitHub」を開き、「Sync now」を押す
3. 一覧の `h-kazuki-pixel/futoko-shien-lod` のスイッチを入れる。ページを読み直して、有効の一覧に出ることを確かめる
4. 次にデータが変わった日に、いつもどおりリリースを作る(タグ `v{年}-{月}-{日}`)。数分で Zenodo に記録ができ、DOI が付く
5. DOI(`10.5281/zenodo.` で始まる番号)をチャットに貼ってもらえれば、README と about と応募文に入れる

結果(11/17): 橋本が v2026-11-17 のリリースを作り、Zenodo に記録ができた(種類 Dataset、Open、作者 Hashimoto, Kazuki・所属あり)。すべての版を指す DOI は `10.5281/zenodo.24292049`、v2026-11-17 だけを指す DOI は `10.5281/zenodo.24292050`。README・about・応募の下書きには、すべての版の方を入れた。Zenodo の公開日は November 16, 2026 と出る(UTC の日付のため。日本時間では 11/17)

## 公開してから確かめたこと(2026-11-15)

`pages` の確認(実行 43632552411)で、公開された12の URL を引いた結果。数え方: curl で転送を辿り、最後の応答の HTTP と形式、最初の応答、`Access-Control-Allow-Origin` を記録した。1件の URI は `40219-fs-hojo` の1件だけで試している。

| 引いた先 | 結果 |
|---|---|
| 12の URL すべて | 転送を辿った後は HTTP 200。`Access-Control-Allow-Origin` は `*`(他のサイトの上のプログラムから読める) |
| `id/40219-fs-hojo` | 最初の応答は 301。1回の転送で `id/40219-fs-hojo/` のページ(text/html)が返る |
| `ns` | 転送なしで `ns.html` が返る(text/html) |
| `.ttl`(全件、1件、語彙、データセット) | `text/turtle; charset=utf-8` |
| `.jsonld`(全件、1件) | `application/ld+json` |
| `seido.csv` | `text/csv; charset=utf-8` |

分かったのは、届くことと形式まで。もの(制度)の URI とページを分ける転送は 303 ではなく 301 で、形式の出し分け(Accept に応じた応答)は無い。データが欲しいときは `.ttl` か `.jsonld` を付ける。

弱い所は `docs/弱い所.md` の「公開の形」に書いた。

`kumiawase/` のページと、統計を引くコードを、別の呼び出しに見せた。表の数字は、数え直して17市町すべて一致。指摘と、その後:
